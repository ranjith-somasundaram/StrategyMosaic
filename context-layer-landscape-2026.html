Architecture explainer

Named together, built for different jobs.

Microsoft, Snowflake, Databricks, Atlan and Strategy come up in the same conversation about "the layer that gives AI trusted context." Read as five candidates for one slot, they look like competitors. They mostly aren't. Three are data platforms, one is a governance & context layer, one is a semantic & consumption layer — and in a real architecture they often sit together as layers, not substitutes. This explains what each is actually for, where they genuinely overlap, and how to think about fit.

How to read this: it's an architecture explainer, not a scorecard with a winner. Every platform here is strong and credible. Where Strategy fits is described as fit, not victory — and where you wouldn't need it is stated plainly. Status (GA vs preview) is point-in-time June 2026 and moves fast; verify specifics before committing.

Why these get named together.

By 2026 every platform ships a semantic layer, a context / ontology layer and an MCP server — and every platform can federate to external data. That convergence is real, and it's exactly why the five look interchangeable on a slide. The differences that remain are narrower and more specific than "who can reach the data" — they're about who owns the governed meaning, what it's optimized for, and how far it reaches into non-database sources. The next sections lay those out plainly.

What each is for

Three data platforms, two horizontal layers.

Described the same way, with the same candor — including what each one deliberately isn't. None of these is trying to be all five things; they're named together because their edges now overlap, not because they do the same job.

Microsoft FabricData platform
Fabric IQ GA · ontology preview
Primary job
Run the Microsoft data estate end to end — OneLake substrate, Power BI semantic models, Fabric IQ context, Copilot & Operations agents.
Best fit
Organizations standardized on Azure and M365 that want one governed stack from storage to agent.
Deliberately isn't
A neutral cross-vendor layer — it's centered on Fabric / Azure, though OneLake now mirrors Oracle, SAP Datasphere and more.
SnowflakeData platform
Horizon · semantic views · Cortex agents
Primary job
A governed data cloud — store, govern and query, now with semantic views, Horizon Context and Cortex agents exposed over MCP.
Best fit
Snowflake-centric estates that want governed analytics and AI without managing infrastructure.
Deliberately isn't
A native BI / visualization tool (it partners for that); semantics are deepest on Snowflake-resident data, broader reach via Iceberg.
DatabricksData platform
Unity Catalog · Genie · Genie Ontology
Primary job
A lakehouse + governance platform (Unity Catalog) that also executes everything, with Genie agents and a new Genie Ontology context layer.
Best fit
Engineering-led teams running data, ML and analytics together on one lakehouse.
Deliberately isn't
A turnkey BI layer; the ontology is brand new. Centered on the lakehouse, though Lakehouse Federation reaches external sources read-only.
AtlanGovernance & context layer
Gartner Leader, D&A Governance 2026
Primary job
A vendor-neutral governance & context layer — enterprise data graph, active metadata and lineage, served to tools and agents over MCP.
Best fit
Large estates that need one trusted context and governance plane across many platforms.
Deliberately isn't
An execution or BI engine — it serves context, never runs the query or renders the answer. It needs platforms underneath it.
Strategy Mosaic + OneSemantic & consumption layer
Mosaic-over-MCP GA · OSI co-founder
Primary job
A vendor-neutral semantic layer (Mosaic) that defines a governed metric once across 200+ sources, plus a consumption layer (Strategy One, Auto, HyperIntelligence) that renders it for people and agents. Mosaic Sentinel adds governance and audit.
Best fit
Multi-vendor or multi-source estates that want one governed definition of a metric usable everywhere — including ERP / CRM / app data like SAP, Oracle and Salesforce.
Deliberately isn't
A data substrate (it owns no storage or compute), a full data-discovery catalog, or the deepest ontology — it's lighter there than Atlan or the platforms, and semantic modelling is real upfront work.

What's converged — and why they look alike

  • Every one now exposes governed data to agents over MCP — that row is all-primary.
  • Every platform ships a semantic layer, a context / ontology layer and agents — the tiers rhyme.
  • Every platform can federate to outside data (Iceberg catalogs, mirroring, query federation). None is a walled garden.
  • "Context layer for AI" became everyone's phrase, so the category language collapsed into one slide.

What still genuinely differs

  • Owns a substrate vs sits across them: the three platforms run storage and compute; Atlan and Strategy don't.
  • Governs access vs governs meaning: platform federation governs table access across sources; a semantic layer unifies the metric definition across them.
  • Renders the answer vs doesn't: Power BI and Strategy render BI for people; Atlan serves context only.
  • Database / lake reach vs app reach: platform federation centers on warehouses, lakes and Iceberg; Strategy's connectors also reach ERP / CRM / on-prem (SAP, Oracle, Salesforce).
  • Incentive: a platform optimizes for its own engine; a neutral layer has no substrate to favor.

The honest takeaway: often layers, not substitutes.

In a real architecture these frequently coexist. A common shape: a platform as substrate + governance (say Snowflake or Databricks), Atlan for estate-wide context and lineage, Strategy for one governed semantic definition and consumption across sources, and Power BI, Fabric or agents on top. The useful question isn't "which one wins" — it's "which layer am I solving for, and what do I already own?"

How to think about it

The questions that actually decide fit.

Not "which one wins" — these don't compete for the same slot. The useful exercise is matching the layer to the need and to what you already run. Five questions an architect can answer honestly:

1. Where should the governed meaning live?
If your data sits in one platform and you intend to stay there, that platform's own semantic layer may be all you need. If a metric must mean the same thing across several platforms — and survive a future migration — a layer that's independent of any one of them (Strategy for semantics, Atlan for context) earns its place.
2. What's your data-residency and sovereignty posture?
In the UAE this often decides the substrate first — Azure UAE, a sovereign cloud, or a specific region. The semantic and context layers should sit above whatever residency dictates, not force a substrate choice.
3. How much of your data isn't in a database?
If almost everything is in one warehouse or lake, platform-native semantics cover it well. If business-critical data lives in SAP, Oracle, Salesforce, mainframe or on-prem systems, a layer built to reach application sources — not just databases and Iceberg — matters more.
4. Do you need to render the answer, or just serve context?
If people need dashboards and natural-language answers, you need a consumption layer (Power BI, Strategy). If you only need agents to have trusted context over data you already govern, a context layer (Atlan) on top of your platform may be enough.
5. One platform or many — today, and in three years?
Single-platform shops get the most from native layers. Multi-vendor estates — common after mergers, or when different teams standardized differently — are where a neutral layer pays for itself.
Where Strategy fits Multi-source, multi-vendor estates that need one governed definition of a metric usable by every tool and agent — including ERP / CRM / app data — plus a way to render it for people. It complements the platform you already run rather than replacing it.
Where you may not need it A committed single-platform shop with all relevant data in one warehouse or lake, whose native semantic layer and BI already meet the need, may get there without an added layer. That's a legitimate outcome — and worth saying plainly.
